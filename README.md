# CERTICOS BOOKS

CDRI 프론트엔드 사전 과제로 구현한 도서 검색 서비스입니다.
카카오 책 검색 API로 도서를 검색하고, 마음에 드는 책을 찜해 둘 수 있습니다.

**기술 스택**: React, TypeScript, React Query, Next.js, Tailwind CSS

<br />

## 1. 프로젝트 개요

### 주요 기능

| 기능      | 내용                                                                            |
| --------- | ------------------------------------------------------------------------------- |
| 도서 검색 | 검색어로 도서를 검색하고, 결과를 10개씩 무한 스크롤로 불러옴                    |
| 상세검색  | 제목·저자명·출판사 중 조건을 골라 검색 (전체 검색과 동시에 진행되지 않음)       |
| 검색 기록 | 최근 검색어를 최대 8개까지 저장하고, 브라우저를 재시작해도 유지                 |
| 도서 상세 | 상세보기로 펼쳐 책 소개·원가·할인가 확인, 구매하기로 상세페이지(새 탭) 이동     |
| 찜하기    | 하트로 찜·해제, 찜한 책은 "내가 찜한 책"에서 확인 (브라우저 재시작 후에도 유지) |

<br />

### 화면

- `/` 도서 검색
- `/likes` 내가 찜한 책

## 3. 폴더 구조 및 주요 코드 설명

```
src/
├── api/                    # 카카오 API 호출 (HTTP 계층)
│   ├── kakao-client.ts     #   axios 인스턴스
│   ├── book.ts             #   책 검색 + 응답을 앱에서 쓰는 형태로 변환
│   └── error/              #   에러 코드별 메시지와 메시지 결정 로직
├── queries/                # api/의 함수를 React Query로 감싼 hook (캐시·무한 스크롤)
├── hooks/                  # API를 호출하지 않는 hook (검색 기록, 찜, 팝업 닫기 등)
├── components/
│   ├── ui/                 #   도메인과 무관한 범용 UI (Button, Select, Toast 등)
│   ├── icons/              #   Figma에서 export한 아이콘 컴포넌트
│   ├── layout/             #   헤더, 콘텐츠 폭 컨테이너
│   └── book/               #   도서 도메인 컴포넌트 (두 페이지가 함께 사용)
│       └── book-list-item/ #     리스트 아이템과 그 부품 (접힘·펼침, 썸네일, 찜 버튼 등)
├── app/
│   ├── (search)/           # 도서 검색 페이지 ("/")
│   │   ├── _components/    #   이 페이지에서만 쓰는 컴포넌트 (검색창, 상세검색 등)
│   │   └── _lib/           #   검색 URL 생성·해석
│   ├── likes/              # 내가 찜한 책 페이지
│   ├── not-found.tsx       # 404 페이지
│   └── error.tsx           # 예상하지 못한 화면 오류 페이지
├── lib/                    # 범용 유틸 (cn, 포맷, localStorage 저장소)
├── providers/              # React Query Provider (전역 에러 처리 포함)
├── styles/                 # Figma 기반 디자인 토큰 (색상, 타이포, 그림자, 브레이크포인트)
└── types/                  # 도서 타입
```

### 컴포넌트 배치 기준

- 한 페이지에서만 쓰면 그 라우트의 `_components/`
- 두 페이지 이상에서 쓰면 `components/` 아래 도메인 폴더 (`book/`)
- 도메인과 무관하면 `components/ui/`

<br />

### 데이터 흐름

```
카카오 API ─→ api/book.ts ─→ queries/book.ts ─→ 컴포넌트
              (응답 변환)      (React Query 캐시)
```

- **응답 변환** (`api/book.ts`)
  - 카카오 응답을 앱에서 쓰는 형태로 바꿉니다. (camelCase, 값이 없으면 `null`)
  - 컴포넌트는 카카오 응답 형식을 직접 다루지 않아서, 응답 형식이 바뀌어도 이 파일만 고치면 됩니다.
- **검색 상태는 URL에** (`/?query=하루키&target=person`)
  - React Query가 결과를 저장하는 기준(쿼리 키)으로 URL의 검색 조건을 그대로 씁니다.
  - 그래서 같은 검색으로 돌아오면 저장된 결과를 즉시 보여줍니다.
  - 일정 시간이 지난 결과는 저장된 결과를 먼저 보여주면서 뒤에서 새로 받아와 갱신합니다. (캐시 시간은 [성능 최적화](#3-성능-최적화) 참고)
- **브라우저 저장소** (`lib/local-storage-store.ts`)
  - 검색 기록과 찜 목록이 함께 쓰는 localStorage 저장소입니다.
  - 저장된 값이 바뀌면 화면도 바로 갱신되고(`useSyncExternalStore`), 다른 탭에서 바꾼 내용도 반영됩니다.

## 4. 라이브러리 선택 이유

| 구분      | 분류       | 라이브러리                            |
| --------- | ---------- | ------------------------------------- |

| 직접 선택 | 프레임워크 | Next.js 16 (App Router)               |
| 직접 선택 | HTTP       | axios                                 |

### 과제 필수 스택의 활용

과제에서 정한 스택은 선택 이유 대신 어떻게 활용했는지 정리했습니다.

#### React Query

- **무한 스크롤**
  - `useInfiniteQuery`로 페이지 번호와 다음 페이지 여부(카카오 응답의 `is_end`)를 관리하고, 스크롤 감지와 연결만 했습니다.
- **쿼리 키 설계**
  - 검색 조건(`query`, `target`)을 쿼리 키로 써서, 같은 검색은 저장된 결과를 재사용하고 조건이 바뀌면 자동으로 다시 요청합니다.
  - 키는 `bookKeys.search(filter)`처럼 한 곳에서 만들어, 키 문자열을 여러 곳에 직접 쓰지 않습니다.
- **전역 에러 처리**
  - `QueryCache`·`MutationCache`의 `onError`로 모든 요청의 에러 안내를 한 곳에서 처리합니다. ([공통 에러 처리](#1-공통-에러-처리) 참고)

<br />

### 직접 선택한 라이브러리

#### Next.js (App Router)

- **기본 기능이 많아 직접 구현할 것이 적음**
  - 파일 기반 라우팅, `next/image` 이미지 최적화(크기별 변환·지연 로딩), `next/font` 폰트 최적화를 별도 설정 없이 사용합니다.
- **파일 규칙으로 페이지 완성도 확보**
  - `not-found.tsx`(404), `error.tsx`(에러 경계), `icon.svg`(파비콘), `metadata`(페이지별 탭 제목·설명)를 정해진 파일·export만으로 구성했습니다.
- **SEO에 유리한 구조**
  - 페이지 틀과 메타데이터가 서버에서 미리 렌더링된 HTML로 제공됩니다.
  - 검색 결과는 브라우저에서 불러오지만, 필요하면 서버 렌더링으로 확장할 수 있습니다.
- **환경 변수와 API 키 관리**
  - `.env`를 자동으로 읽고, `NEXT_PUBLIC_` 접두사로 브라우저에 노출할 값을 명시적으로 구분합니다.
  - 이 과제는 로컬 실행이라 브라우저에서 직접 호출했지만, 실서비스에서는 Route Handler로 키를 서버에만 두는 방식으로 쉽게 전환할 수 있습니다.
- **서버·클라이언트 컴포넌트 분리**
  - 상호작용이 필요한 부분만 클라이언트 컴포넌트로 두어 브라우저로 보내는 JavaScript를 줄일 수 있습니다.

#### axios

- **설정을 한 곳에서 관리**
  - 인스턴스 하나에 baseURL, 카카오 인증 헤더, 타임아웃을 두고 모든 요청이 공유합니다.
- **편한 파라미터·에러 처리**
  - 쿼리 파라미터를 객체로 넘기면 인코딩해 주고, HTTP 에러 상태를 자동으로 에러로 던집니다.
  - `isAxiosError`·`isCancel`로 에러 종류를 쉽게 구분할 수 있어 공통 에러 처리에 활용했습니다.

#### Tailwind CSS v4 + clsx + tailwind-merge

- **디자인 토큰을 그대로 클래스로**
  - Figma의 색상·타이포·그림자를 `@theme`과 `@utility`로 정의해 `text-primary`, `typo-title3`처럼 바로 씁니다.
  - 시안 값과 코드가 1:1로 대응됩니다.
- **App Router와의 궁합**
  - 빌드 시점에 CSS를 만들어 서버 컴포넌트에서도 별도 설정 없이 동작합니다.
  - CSS-in-JS(Emotion)는 App Router에서 SSR 스타일 수집 설정이 필요해 사용하지 않았습니다.
- **반응형이 간단함**
  - `md:`, `desktop:`(본문 폭 기준 커스텀 브레이크포인트) 같은 접두사로 화면별 스타일을 같은 자리에서 관리합니다.
- **clsx + tailwind-merge**
  - `clsx`로 조건에 따라 클래스를 붙이고, `tailwind-merge`로 같은 속성의 클래스가 겹치면 나중 것만 남깁니다.
  - 직접 만든 타이포 클래스(`typo-*`)도 겹침 규칙에 등록해, 버튼 같은 공통 컴포넌트에 바깥에서 `className`을 넘겨 스타일을 안전하게 바꿀 수 있습니다.

#### Vitest

- **설정이 간단하고 빠름**
  - TypeScript를 별도 변환 설정 없이 실행하고, 28개 테스트가 약 0.2초에 끝납니다.
- **Jest와 비슷한 API**
  - `describe`, `expect`, `vi.mock` 등 익숙한 방식으로 작성할 수 있습니다.

## 5. 강조하고 싶은 기능

### 1) 공통 에러 처리

**문제**

- 화면마다 에러 코드를 확인하고 메시지를 띄우는 코드를 작성하면, 같은 에러에도 화면마다 다른 문구가 나오기 쉽습니다.
- 문구를 바꿀 때 여러 파일을 찾아 고쳐야 해서 유지보수가 어렵습니다.

**해결**

에러 코드별 메시지를 한 곳에서 관리하고, React Query의 전역 에러 처리에서 한 번에 안내합니다.

```
요청 실패 → QueryCache·MutationCache의 onError → 에러 코드로 메시지 결정 → 토스트로 안내
```

| 파일                                 | 역할                                                     |
| ------------------------------------ | -------------------------------------------------------- |
| `api/error/error-messages.ts`        | 에러 코드 → 기본 메시지 매핑 (문구 수정은 이 파일만)     |
| `api/error/resolve-error-message.ts` | 에러 응답에서 코드를 꺼내 보여줄 메시지를 결정           |
| `providers/query-provider.tsx`       | 모든 query·mutation의 에러를 전역에서 받아 토스트로 표시 |

```ts
new QueryClient({
  queryCache: new QueryCache({ onError: handleError }),
  mutationCache: new MutationCache({ onError: handleError }),
});
```

**카카오 API에 맞춘 부분**

카카오는 API마다 에러 응답 형식이 달라서, 실제로 각 API를 호출해 형식을 확인하고 두 형식 모두에서 코드를 꺼내도록 했습니다.

| API                 | 에러 응답                                                | 코드 위치            |
| ------------------- | -------------------------------------------------------- | -------------------- |
| 책 검색 (다음 검색) | `{ "errorType": "AccessDeniedError", "message": "..." }` | `errorType` (문자열) |
| 카카오 공통         | `{ "code": -401, "msg": "..." }`                         | `code` (숫자)        |

- 응답 자체가 없으면(오프라인 등) 네트워크 오류 메시지를, 매핑되지 않은 코드는 기본 메시지를 보여줍니다.
- 검색어가 바뀌어 취소된 요청은 에러로 안내하지 않습니다.

**결과**

- 화면 코드에는 에러 메시지 로직이 없습니다.
- 새 API를 추가해도 같은 규칙이 자동으로 적용됩니다.
- 지금은 요청이 도서 검색 하나라 모든 요청에 같은 규칙을 적용합니다.
- 화면별로 메시지를 끄거나 바꿔야 하면 요청의 `meta`에 예외 설정을 두고 `onError`에서 확인하도록 확장할 수 있습니다.

### 2) URL 기반 검색 상태

**문제**

- 네트워크를 3G로 제한해 테스트하던 중, 검색어를 입력하고 Enter를 눌러도 몇 초 동안 로딩 표시조차 뜨지 않는 문제를 발견했습니다.
- 원인은 `router.push`였습니다.
- Next.js는 검색 파라미터가 바뀌면 다른 페이지로 보고 새 URL의 페이지 데이터를 서버에 먼저 요청합니다.
- 이 페이지는 서버에서 검색어를 쓰지 않으므로 기다릴 필요가 없는 요청이었습니다.

**해결**

- URL만 바꾸는 브라우저 history API를 사용했습니다.
- Next.js는 `history.pushState`를 감지해 서버 요청 없이 `useSearchParams`를 바로 갱신합니다.

```ts
// router.push 대신
window.history.pushState(null, "", `/?${params}`);
```

검색 상태(`query`, 상세검색 조건 `target`)는 URL 한 곳에만 둡니다.

```
/?query=하루키                → 전체 검색
/?query=하루키&target=person  → 상세검색 (저자명)
```

- `target`의 유무로 전체 검색과 상세검색을 구분하므로, 요구사항인 "두 검색은 동시에 진행할 수 없음"이 URL 구조로 보장됩니다.

**결과**

- Enter를 누르는 즉시 검색이 시작됩니다.
- 새로고침하거나 링크를 공유해도 같은 검색 결과가 보입니다.
- 뒤로가기를 하면 이전 검색 결과(스크롤로 불러온 페이지 전체)가 저장된 데이터로 즉시 그려집니다.
- 목록이 바로 그려지므로 브라우저가 이전 스크롤 위치로 정확히 돌려놓습니다. (데이터를 새로 불러와야 했다면 목록이 짧은 상태라 스크롤 위치를 복원하지 못함)

### 3) 성능 최적화

**문제**

- 리스트 아이템마다 찜 목록 전체를 구독하고 있어서, 하트 하나를 누르면 불러온 아이템 전체(무한 스크롤로 수십~수백 개)가 다시 그려졌습니다.
- 무한 스크롤로 다음 페이지가 추가될 때도 이미 그려진 아이템까지 다시 그려졌습니다.

**해결**

- **필요한 값만 구독**
  - localStorage 저장소에 `select` 옵션을 추가해, 각 아이템이 찜 목록 전체가 아니라 "이 책의 찜 여부(boolean)"만 구독합니다.
  ```ts
  const isLiked = useLocalStorageStore(likedBooksStore, (books) =>
    hasBook(books, book),
  );
  ```
- **바뀌지 않은 아이템은 건너뛰기**
  - 리스트 아이템을 `memo`로 감쌌습니다.
  - React Query는 바뀌지 않은 데이터의 참조를 유지(구조적 공유)하므로, 다음 페이지가 추가돼도 기존 아이템에는 같은 객체가 넘어와 다시 그리지 않습니다.
- **필요 없어진 요청 취소**
  - 검색어가 바뀌면 React Query가 주는 `AbortSignal`로 이전 요청을 취소합니다.
- **도서 검색 캐시 시간 5분** (`staleTime`, 앱 공통 설정은 1분)
  - 무한 스크롤 쿼리는 다시 불러올 때 받아 둔 페이지를 모두 다시 요청합니다.
  - 5페이지까지 내렸다면 5번 요청합니다.
  - 검색 → 상세보기 → 다른 검색 → 뒤로가기처럼 오가는 사이에 1분은 쉽게 지나서, 그때마다 여러 페이지를 다시 요청하게 됩니다.
  - 도서 정보는 몇 분 사이에 바뀌는 데이터가 아니므로, 5분 동안은 다시 요청하지 않고 저장된 결과를 보여줍니다.

**결과**

- 하트를 누르면 그 아이템 1개만, 다음 페이지를 불러오면 새로 추가된 아이템만 그려집니다. (React DevTools Profiler로 확인 가능)
- 검색 결과를 오가도 5분 동안은 같은 페이지들을 다시 요청하지 않습니다.

<br />

### 그 밖에

- **단위 테스트** (Vitest, 28개, 화면 컴포넌트 테스트는 범위 밖)
  - 카카오 응답 변환 (정가 0·할인가 -1 → `null`)
  - 에러 메시지 결정
  - 검색 기록 규칙 (중복은 맨 앞으로, 최대 8개), 상세검색 URL 규칙
  - localStorage 저장소
- **접근성**
  - 본문 바로가기 링크, `aria-expanded`·`aria-pressed`
  - 겹쳐 열린 팝업은 Escape로 가장 나중에 열린 것만 닫기
  - 동작 줄이기 설정 존중

## 6. 구현 시 판단한 사항

시안과 요구사항에 명시되지 않은 부분은 아래처럼 판단해 구현했습니다.

### 데이터

- **API 키**
  - 배포 없이 로컬에서 실행하는 과제라 브라우저에서 카카오 API를 직접 호출합니다.
  - 실서비스라면 키가 노출되지 않도록 서버에서 중계해야 합니다.
- **가격 표시**
  - 판매가는 할인가로 봅니다.
  - 실제 검색 결과 1,000권을 확인해 보니, 할인가가 없는 책의 93%는 판매 상태 정보도 없는 책(절판 등)이었습니다.
  - 그래서 할인가가 없을 때 정가를 지금 살 수 있는 가격처럼 보여주지 않고 `-`로 표시합니다.
  - 펼친 상태에서는 원가·할인가를 항상 보여주고, 취소선은 둘 다 있을 때만 긋습니다.

<br />

### 검색

- **목록 방식: 무한 스크롤**
  - 요구사항은 "페이지당 10개"까지만 정해져 있고, 페이지네이션과 무한 스크롤 중 어떤 방식인지는 명시되지 않았습니다.
  - 검색 결과는 관련도 순으로 위에서부터 훑어보는 화면이라 특정 페이지로 이동할 일이 적습니다.
  - 모바일 우선으로 작성한 만큼, 스크롤로 이어 보는 방식이 더 자연스럽다고 판단했습니다.
  - 시안에도 페이지 이동 UI가 없습니다.
  - 무한 스크롤의 단점인 뒤로가기 시 위치 유실과 목록이 길어질 때의 성능 저하는 캐시와 렌더링 최적화로 보완했습니다. ([URL 기반 검색 상태](#2-url-기반-검색-상태), [성능 최적화](#3-성능-최적화) 참고)
- **빈 검색어**
  - 검색어를 지우고 Enter를 누르면 초기 화면으로 돌아갑니다.
  - 시안에서 초기 화면을 "검색 결과 없음" 화면과 같게 정의하고 있어서, 빈 검색어를 검색 초기화로 해석했습니다.
- **상세검색**
  - 요구사항("전체 검색과 상세 검색은 동시에 진행 불가")에 따라, 상세 검색을 하면 검색창을 비우고 전체 검색을 하면 상세검색 조건을 초기화합니다.
  - 검색 기록 저장은 요구사항에서 검색창 기능으로 정의되어 있어서, 상세 검색어는 기록에 저장하지 않습니다.

<br />

### 화면

- **대체 표시**
  - 썸네일이 없거나 불러오지 못하면 책 아이콘, 책 소개가 없으면 안내 문구를 보여줍니다.
- **목록 요약**
  - 접힌 목록에서는 저자를 "OOO 외 N명"으로, 제목은 2줄까지 보여주고 마우스를 올리면 전체 제목을 볼 수 있습니다.
  - 펼친 상태에서는 모두 보여줍니다.
- **반응형**
  - 시안이 데스크톱만 있어 모바일 우선으로 작성했습니다.
  - 도서 리스트는 본문 폭(960px)부터 시안 배치를 적용하고, 그보다 좁으면 [썸네일 | 정보] + 아래 줄 버튼으로 배치합니다.
  - 글자 크기는 공간이 부족해 레이아웃이 깨지는 곳(헤더, 404·에러 제목)만 줄이고, 나머지는 시안 크기를 유지했습니다.
